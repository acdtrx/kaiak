Gateway internals

What happens inside the kaiak binary: the packages it is made of, the path a request takes through them, and how the gateway boots, reloads config and shuts down.

At a glance

  • One static Go binary, standard library only. No third-party code, no external services. gateway/cmd/kaiak builds the dependency graph and owns shutdown; every subsystem is a package under gateway/internal/, and Go's internal/ visibility plus its ban on import cycles keep the boundaries.
  • Two listeners. API on :8080 (OpenAI format: chat completions, completions, embeddings, models) and admin on :9090 (/healthz, /readyz, /metrics). Only the API port faces clients.
  • Two config modes. File mode (KAIAK_CONFIG_FILE, reload on SIGHUP, limits kept locally) or control-plane mode (KAIAK_CONTROL_URL + KAIAK_CONTROL_TOKEN, config pushed live, usage and status reported back). The second is covered in the integration page.
  • Stateless by default. It writes nothing to disk unless KAIAK_DATA_DIR is set. Usage not yet delivered waits in memory; the drain delivers it.
  • Two hard fences. Only provider opens connections to model backends; only control talks to the control plane.

Packages and how they connect

The server package owns the listeners and the request pipeline; it calls the stage packages in a fixed order. Everything that talks to the outside world is behind one of two packages.

The request pipeline

Every client request passes the same ordered stages — no endpoint or fast path skips one. New cross-cutting behavior (caching, guardrails, prompt logging) arrives as a new stage, not as a special case inside a provider.

What each stage does

  • Admission — refuses during a drain and while no config is in force, before anything is read.
  • Auth — hashes the bearer key, looks up key ID and its group (with the group's path up the tree), then counts the request against the key's concurrency limit.
  • Inbound — reads the body under the per-request cap and the gateway-wide body budget, parses only the fields the gateway owns and keeps the raw bytes for passthrough; then the model-access check and the model's defaults and output limit.
  • Limits — checks every scope on the key's path (global › each ancestor group › the key's group) and reserves input estimate + output limit.
  • Routing — picks the deployment with the fewest requests in flight among those with a closed circuit and a free backend slot; otherwise waits in the model's FIFO queue.
  • Accounting — opens the attempt's meter; the relay feeds it every event.
  • Provider — edits only what the gateway owns (model name, output limit, usage flags) and forwards everything else untouched; returns events in the client's format for server to relay.

Routing and reliability

A public model name maps to one or more deployments (backend + the model's name on that backend) — identical copies. There is no fallback to another model.

  • Concurrency cap per backend (max_in_flight), split among live gateways in control-plane mode (cap ÷ live count, rounded up). A request that finds no free slot waits in its model's queue (default 100 deep, 30 s): full → 429 queue_full, timed out → 429 queue_timeout.
  • One dispatcher under routing's lock hands each freed slot to the longest-waiting request that can use it; a waiting request blocks on its own channel — no goroutine per waiter.
  • 429 cooldown: a deployment that answered 429 is avoided for a while, and the request retries elsewhere.
  • Model check: every applied config's backends are listed once in the background; a deployment whose model is not listed is logged as a warning.

Limits and accounting

Keys belong to a group in one generic tree (up to 8 levels, shaped per deployment: team › project › env › workload, a users group whose children are people, …); global is the root above the top-level groups. A request's scopes are global plus every group on its key's path. It must pass every limit of each scope, and its usage counts toward each. Keys have no limits of their own. Allowed models intersect down the path, and no list anywhere on the path means every model. A group's child_defaults give each direct child default models and limits — defaults, not ceilings: a child's own list or limit replaces them, so hard restrictions for a subtree go on the parent's own lists and limits. Every effective limit is a counter on every gateway (about 1.4 KB), so a config holds at most 50 000 of them. Refusals say group limit or global limit — never a group ID or label; the log line names the group.

  • Before the request runs: input tokens are estimated from the body (about 4 bytes per token; each image or audio item a flat 1000). The reservation is that estimate plus the output limit.
  • Output limit: each model has a default (injected when the client sets none) and a ceiling (requests above it are lowered).
  • Accounting reads the backend's usage report from the relayed response (the usage chunk is read even when withheld from a client that did not ask for it). Missing report → the record is flagged estimated; a response that stopped early → partial, billed for what was relayed.
  • One record per routed request, plus one per retried attempt that reached the backend and got no answer. Each carries the key's group path (groups, top-level first), so the control plane counts it toward every group on it. Requests refused before routing produce none.
  • Units: tokens_in (uncached), tokens_cached, tokens_out (reasoning included), tokens_reasoning (visibility only). Cost is in nano-USD from the price table in force on the request's UTC date.
  • Metrics and usage records are separate paths. Metrics are cheap and approximate for dashboards; records are exact and idempotent for billing. Neither is derived from the other.

Config: one apply path

Lifecycle

Boot

  • File mode: load the file; failure exits. Listeners bind once the config is in force.
  • Control-plane mode: fetch the snapshot, retrying for up to KAIAK_CONTROL_BOOT_WAIT_MS (60 s); if the control plane stays unavailable, use the last-known-good copy (with a data dir), then the seed config, else exit so the supervisor restarts it. Readiness also waits for the first totals (normally milliseconds — they follow the config on the stream). Details on the integration page.
  • Listeners bind only when ready, so probes see a closed port during boot — size the startup probe for the boot wait.

Drain (SIGTERM or SIGINT)

  • Client timeouts bound a client's progress, never a whole response: headers 30 s, body read 60 s, each write 60 s, idle keep-alive 120 s. A stream runs as long as the backend generates and the client reads.
  • Optional connection cap (KAIAK_MAX_CONNECTIONS) closes excess connections before reading a byte; the admin listener is never capped.

Extension points and the road ahead

The gateway is built around seams, not features (docs/kaiak.md, principle 5): v1 fills each seam with the minimum. New APIs, new backends, caching, guardrails and non-token models are meant to arrive as new plugs in an existing seam, not as rewrites. Two project rules constrain every future plug:

  • One pipeline, no side doors. New cross-cutting behavior is a new pipeline stage, never a special case inside a provider or a fast path around a stage.
  • Features earn their place. Nothing below is scheduled. Each item waits in docs/BACKLOG.md with a revisit trigger: the observed need that would justify building it.

Anthropic at both ends

Anthropic can arrive at either end: as a client API (inbound ①) and as a backend (provider ③). The rule deciding the work is passthrough first (principle 4). When both sides speak the same API, forward it with the few edits the gateway owns. Translate only when they differ, because translation loses backend-specific fields.

Observability

  • Logs: one line per request (JSON by default, KAIAK_LOG_FORMAT=text for development); config loads log their trigger and result. Never a client key, provider secret, prompt or response.
  • Metrics on the admin port (optionally behind KAIAK_METRICS_TOKEN): ops metrics from the pipeline, usage metrics from accounting (labelled key_group — the key's group; not group, a common scrape target label —, root_group — its top-level group —, key_id, model, status; global.metrics.group_label and key_id_label switch the first and third off to bound series), control-plane connection state (kaiak_control_outage, kaiak_control_config_mismatch), delivery metrics from the batch sender. Every series with config-bounded labels exists at 0 from startup; usage series appear with traffic.
  • Limit refusals carry Retry-After and rate-limit headers; X-Request-Id ties a response to its log line and usage record.
