Gateway ↔ control plane

How N gateway replicas and one control plane divide the work: the control plane decides and keeps the records, the gateways serve and report — and keep serving when the control plane is gone.

The gateway only makes outbound calls. There is one shared bearer token (KAIAK_CONTROL_TOKEN), every request and response carries Kaiak-Protocol: 5, and the gateway names itself in Kaiak-Instance (default: the hostname / pod name). A version mismatch is refused on both sides — the halves move together.

The three endpoints

Boot and steady state

When the control plane is unavailable at boot

  1. Keep opening the stream until its first config arrives or the boot wait runs out (KAIAK_CONTROL_BOOT_WAIT_MS, 60 s). Before the first publish the stream is open but carries no config.
  2. With a seed file (KAIAK_SEED_CONFIG_FILE): boot from the seed — free models only, so nothing is served without its budget. Status reports ready with applied_config_hash: null.
  3. Otherwise exit non-zero; the supervisor (Kubernetes) restarts it with backoff.

Whichever way it booted, the gateway keeps trying the control plane and switches to its config at first contact.

Config pushes

One current config, ordered by its sender

  • The control plane holds one current config and its config_hash (SHA-256 of its JSON as sent). The hash says what a config is, never when: a gateway applies whatever config its stream sends, skipping one identical to the config it runs or to the one it last rejected.
  • Order is the sender's job. A core sends on a stream what it read last, by when it issued each read, never by a value the store returns: a config read issued before a config already sent there is dropped. Configs and totals are ordered apart — totals do not depend on the config. Each stream also skips a config whose hash is the last it sent.
  • A restored store is the current state. After a restore from a backup, or a failover to a copy behind, the store's config and totals go out like any other; nothing tells a restore apart. Rejected: gateways accepting only a newer config, which would leave them on a config the control plane no longer has; detecting a rollback from a store sequence, which arrives out of order on ordinary traffic, so the check fires with no restore.
  • Slow readers: config events queue and are never dropped; totals never queue (the windows changed meanwhile gather and go out together on drain); a stream that takes nothing for 30 s is closed and the gateway reconnects. Ending a stream stops every send on it at once.

Usage delivery: at least once, counted exactly once

  • Retried with the same ID on network errors, 5xx, malformed acks, and an ack naming another batch. A batch is counted whether or not a config is published.
  • Dropped (logged at error) only when the batch itself can never be accepted: usage-batch-invalid, a message-rule code, instance-mismatch, request-invalid. Retrying it would block every batch behind it.
  • Retried, not dropped, on 401, protocol mismatch, unknown answers — a misconfigured proxy must never discard billing data.
  • Memory bound: at most KAIAK_USAGE_MEMORY_BYTES (64 MiB) of encoded records wait; the drain spends its last 10 s delivering them.

Budgets across gateways

  • Count everything, limits on top: totals carry every scope and type with usage, whatever the config, and the gateway counts its own usage the same way; a limit is a check over its scope's count. So a gateway running a config it was moved off (it rejected the newest) still enforces the spend of a limit the newest dropped, and a limit added mid-window starts with the window's usage.
  • Complete, then changes: a stream's first totals are complete; later ones list only the windows that changed, and a window not listed keeps its value. One store read per push serves every stream of a core.
  • On the stream only: totals travel only on the gateway's stream, never on acks. After an ack the gateway keeps counting that batch as its own until the next push (about a second); a push's counted_through — the instance's last counted batch of each epoch — retires it. An acknowledged batch no push has covered keeps the gateway waiting: past the outage grace that is an outage, so totals that stop coming are never mistaken for no spend.
  • Exact sums: used travels as a decimal string (nano-USD for money), summed as BigInt — a month of spend can exceed what a JavaScript number holds exactly.
  • Totals per scope: a scope (global or a group) holds at most one limit per type, and a limit's identity is (scope, type); a totals window names its group, or none for a global limit. A record adds to the windows of every scope on its groups path, whether or not a limit is there: an edited limit keeps its spend, a limit added mid-window starts with the window's usage, and publishing never waits on counting.

Budgets on the group tree

Status and the live set

  • A status carries state (ready, draining), started_at, the applied config's config_hash, last_rejection (by hash), per-backend in-flight counts and caps with each deployment's circuit, and per-model queue depth.
  • Sent at start, on every stream connect, on change (state, config, rejection, a queue becoming empty or non-empty, a circuit opening or closing — at most one such report a second) and every 10 s. A failed report is simply replaced by the next.
  • A gateway joins the live set with its first status and leaves when silent for 30 s (sweep every 5 s). A draining gateway stays live until it goes quiet, since it still spends. The live count drives per-minute shares and cap splits, and is pushed again when it changes.
  • Two processes under one instance name (a copied KAIAK_INSTANCE_ID) show as alternating started_at values and get a conflict flag in gateways().

Control-plane outages

During an outageBehavior
ServingContinues on the current config and the last pushed totals. The control plane is never in the request path.
Per-minute limitsEnforced locally as before, on the last known share.
UsageHeld in memory and sent in order on reconnect, each record into the window it was used in.
Priced models under a USD limitServed until the outage passes global.control_outage_grace_ms (15 min), then 503 budget_unavailable until contact returns. Free models keep serving.
What counts as contactBytes on the stream (heartbeats included). Usage acks and status reports do not count: neither brings totals. Usage batches unanswered past the grace also count as an outage, even with the stream open, and so do acknowledged batches no totals have shown counted past the grace.
ReconnectReopen the stream — it sends the current config, then the totals — and send the held batches in order.
